# 文案与旁白规范

写作或修改画面标题、正文、要点、旁白和试听稿时读取。使用简洁、专业、平实的产品说明语体：名称准确、逻辑清楚、信息充分，朗读自然。避免套话、闲聊和生硬的公文表达。

本规范约束 Agent 新写或获准修改的文字。已有确认稿和用户要求保留的引文按原意使用；不要在配音合成或字幕对齐阶段擅自改写，也不要为了符合文风修改真实截图中的产品文字。

## 事实与信息密度

- 先根据用户要求确定视频受众和用途。面向产品用户的介绍围绕可完成的任务、呈现方式和输出结果展开；内部开发过程、版本沿革和兼容实现不自动成为卖点。演示所用设备或素材只是示例，不代表产品仅支持这些对象；只有型号、平台或版本影响用户选择、实际限制，或用户明确要求时才具体点名。更新说明和技术讲解按其用途保留必要细节。
- 每段只展开一个功能或场景，说明必要的操作、结果或使用条件。保留专业名词和关键限制，用准确动词表达，不用情绪、形容词或同义句填充篇幅。
- 先核对产品的实际功能、版本和素材。开发初衷只用创作者提供的原因；不虚构经历，不把一般功能说成独创，不贬低未核对的其他产品。
- 不重复画面中已经清楚的按钮和菜单名称，除非需要引导操作。段首不预告要讲什么，段尾不再换句话重复本段结论。
- 简洁不等于极短句堆砌或删掉关键能力。正文可提炼，旁白应保持句意连贯；用户确认的原稿不因版面限制被擅自压缩。
- 对空泛评价做通用句检查：换成另一款产品仍可原样使用，且没有说明具体功能、条件或结果时，删除评价，或用现有依据补清机制。常见但必要的功能事实和操作说明可以保留；不要为了显得具体编造数字、用户反馈或案例。
- 保留稿件中有用的细节，包括格式、版本、数量、适用条件、限制和确定程度。“可能”“目前”“仅支持”等词表达真实边界时不能删除，也不能把有依据的细节改成“显著提升体验”等笼统结论。

## 句式与措辞

- 禁用反问、设问和自问自答。不要用“你是否也遇到过”“是不是很方便”“难道还需要”等句式引导受众，也不要先提问再给答案。标题用“功能概览”“字幕对齐”等直接名称。
- 禁用空泛的宣传与 AI 常见套话，例如“赋能”“开启全新体验”“重新定义”“释放无限可能”“让创作更高效”。真实功能或正式名称包含相同词语时按事实使用，不能机械替换成另一套空话。
- 不用“这段视频将带你了解”“接下来让我们看看”“值得一提的是”“总而言之”等串场填充，也不用连续排比、感叹号、刻意对仗或“不是……而是……”制造气势。
- 避免过度口语化的“搞定”“一把梭”“随便点点”“省心省事”“想怎么用就怎么用”等表达。用“导出”“切换”“保留”“对齐”“复用”等具体动词；不以“实现……赋能”“进行……方面的优化”等名词堆砌假装专业。
- 不添加“完美”“极致”“绝对安全”“保证不丢数据”等没有证据支持的承诺。只有恢复点时，就说明可恢复到哪个状态，不扩大能力范围。
- 删除假洞见和对读者的无效提示，例如“很多人忽略的一点”“真正值得关注的是”“这比看起来更重要”；直接说明已有事实或作用，不用“最重要的是：”制造揭晓感。正常的列表标签、格式名称和标点照常使用。
- 删除功能后面没有事实支撑的评价，如“体现了对体验的持续追求”“标志着新的里程碑”。确需介绍意义时，说明有依据的使用结果。“研究表明”“行业普遍认为”等归因必须有可核对的来源，不能把不确定意见写成共识。
- 同一对象保持同一名称，不为避免重复而轮换“助手”“工具”“引擎”。确属不同组件时保留区别。用具体动作说明能力，避免“作为核心枢纽”“构建完整闭环”等无法解释工作方式的表达。

## 结束位置

最后一项实际信息表达完整后即可结束，不为结构完整额外增加总结段、口号、升华或礼貌收尾。

不要自动补“所有工作都在本地”“数据始终属于你”“一切尽在掌握”“让你专注真正重要的事”“让工作从此更简单”等泛化表态。收尾可以是最后一项功能的明确结果，或用户要求且确有依据的下载、安装、使用入口；没有明确行动入口时不要虚构号召。

用户明确要求介绍本地处理、隐私或数据流时，按真实边界写清具体环节。例如本工具使用云端配音时，不能写“全程离线”或“所有处理都在本地”。技术文档中的必要说明不自动变成产品视频的结束语。

删除空泛片尾后，不再换成另一句更精致的比喻、金句或总结。只有用户要求且有依据时才添加下一步操作；已有完整结果可以直接作为结尾。

## 改写尺度

以下示例只用于对照语体；实际成稿仍需产品依据。

| 避免 | 合适的表达 |
| --- | --- |
| 还在为字幕对不齐而烦恼吗？ | 字幕根据配音时间戳对齐。 |
| 点几下就全搞定了，用起来特别省心。 | 按章节生成配音、字幕和视频。 |
| 强大的主题系统，为你开启全新视觉体验。 | 支持深色与浅色主题，可分别展示或并排对照。 |
| 从一句介绍到完整演示，让创作拥有更多可能。 | 文案、界面截图和操作演示可在同一时间轴编排。 |
| 最后，所有工作都在本地，一切尽在掌握。 | 删除该句；上一句已表达完整时直接结束。 |

只修改有具体问题的句子。保留清楚的原句、作者提供的开发初衷、必要的长句和自然停顿；不把所有段落统一成同样的长度或“结论、解释、总结”结构。专业感来自准确表达，不靠生硬公文词，也不靠把内容全部改成聊天口吻。已有确认稿与用户要求保留的引文继续遵守本规范开头的边界。

画面标题、要点与旁白按各自用途编排，不为装饰增加小标题、emoji、强调词或字幕中的 Markdown 标记；列表在确有并列信息时使用。中文标点和技术名称按正常语法保留，不机械套用英文禁词或标点计数。

## 配音生成

- 先完成文稿，再生成语音。语气提示用于朗读方式，不能代替文案编辑；TTS 不负责替稿件去除套话或冗余。
- 默认语气专业、平稳，发音清晰，语速适中，按语义自然停顿；重音克制，陈述句自然收尾。避免闲聊、促销、夸张播报和每句刻意上扬，也不要逐词机械重读。
- 保留用户指定的角色、语速和语气。默认指导只在未指定时使用，并仅发送给支持该能力的音色；不为了文风自动换声或合成多个角色。
- 用标点组织句意，避免一长串并列项。长稿按场景拆章，单章不超过引擎 2000 字符限制。不要通过大幅加快语速塞入冗余内容。
- 英文名称、版本和缩写按需要做短试听，发音词典只修正明确问题。角色语言不会自动翻译原稿。字幕跟随实际配音，不能把精简后的画面要点冒充逐字字幕。

## 交付或合成前检查

新稿或获准改写稿完成后，读取 [文案复核清单](narration-review.md)，逐句记录具体问题，修正后复核。用户只要求检查时，输出原句、问题类型和修改方向，不改原稿。复核完成后再交付稿件或进入已获授权的配音流程；无需为常规编辑增加一轮确认。

结合画面检查信息重复、术语一致性和阅读节奏。正文的标题、要点与片尾同样遵守本规范。镜头结构见 [content.md](content.md)，不要求每句话都对应一张截图。
